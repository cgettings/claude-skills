### Validating the instrument

- **Citing a `file:line` as evidence means opening that file.** A grep hit proves the string exists, not that anything runs it - count occurrences rather than finding one, because an identifier appearing exactly once in its file is a declaration nothing consumes. That is how a dead `renderer: "svg"` literal became a false claim in both a source comment and a commit message.
- **A code comment is a claim, not evidence, and quoting it into a doc launders it into one.** `smoke-pages.mjs:246` attributed a flake to "several pages contending for one `hugo server`'s on-demand render"; the project CLAUDE.md repeated the phrase, and it was then used as a diagnosis (both corrected 2026-08-23, once it was measured). Measured, it is unsupported: at concurrency 6 against 1 over 12 pages, navigation slowed 1.34x, JS settle time 1.00x, and all 12 reached identical final DOM states `[2026-08-23]`. Opening the file proves the comment exists - the check the `file:line` rule above asks for - and that is not enough when the thing cited is itself prose.
- **A null result from an instrument you have not validated is not a result.** Before reporting "nothing fired" - or building on it - prove the probe can fire at all with a positive control. Null results conceal their own failure: a probe that never reached the code under test and a code path that never ran are indistinguishable in the output.
    - The same applies to searches, in both directions: a pattern the shell mangled (`$'…'` survives as a bare argument but collapses to the empty pattern - matching every line - once nested inside `$( )` in a double-quoted string; the tell is a count equal to the file's line total `[verified 2026-08-19: grep -c $'\r' returned 0 bare and 125 nested, on a 125-line file with zero CR bytes]` - and the bare form is no better at detecting CRs that *are* present, returning 0 on a 69-line CRLF file `[verified 2026-08-21: od showed a CR on every line; count CR bytes with tr -dc CR piped to wc -c, not with grep]`), a tool whose domain silently excludes the target (`git grep` skips untracked files), or a well-formed pattern that simply cannot match a variant of the name it seeks (`lib-[a-z-]+\.html` cannot match `lib-d3.html`; `arquero\.[a-f0-9]*\.js` cannot match `arquero.min.<hash>.js`) yields a confident count that describes the search, not the code. The third has no error to notice, so prefer the shape that cannot have it: for "which members of set X are present", enumerate what is actually there and compare, rather than grepping once per expected member.
    - **"Unchanged" is a null result too, and the comparison is the instrument.** A prefix, a length, or any field the encoding holds fixed reports "no change" against an artifact that did change - a fixed-size QR GIF shares its header, so a prefix check called a regenerated code stale. Compare whole values, and on two known-different inputs first. The mirror case reports change where there is none: `git cherry` compares patch-ids, so a commit reworked or squashed on its way in reads as unmerged though its content is present. The checkable form is tree identity, not a commit list: `git merge-tree --write-tree <base> <branch>` printing `<base>^{tree}` means the merge contributes zero bytes `[verified 2026-08-25 on PR #1458, which `git cherry` called three commits outstanding]`. Differing trees settle nothing the other way - the merge diff is positional, so content the base already carries at another line reads as an addition.
    - **A no-op proof is scoped to the unit you compare, not to the change you meant to test.** Strip-and-diff answers about the *file*, so a second change sharing it breaks the proof: "strip every `class=`, all 7 files identical" was recorded as passing and fails on 2 of 7, which also carry another task's `alt` additions. Compare the commit's parent tree to its staged tree; a per-task commit split makes it exact for free.
- **A check that only asks "did it succeed" passes on a degenerate result.** Assert the parsed value's type or shape, not that parsing returned: `json.loads` hands back a `str` and raises nothing for a document double-encoded as a JSON string literal, which is how "the emitted JSON parses" passed a whole site's JSON-LD that no consumer could read `[2026-08-21]`. Same shape for a 200 response carrying an error page. Incident in the `feedback-verify-my-own-verification` memory in the `EH-dataportal` project store.
- **A line-oriented search assumes one record per line; when the thing being counted can span lines, the count is wrong and looks right.** `grep '<img' | grep -v 'alt='` scores the opening line of every multi-line tag as a miss `[verified 2026-08-21: the sweep returns 16 on EH-dataportal's themes/dohmh/layouts at HEAD and the true figure is 15 - one tag carried its alt two lines below the <img, and the plan asserting 16 had run the same sweep]`. Distinct from the three search failures above: the pattern is well-formed and does match. Count over parsed output - built HTML through a DOM query or axe - rather than over source lines.
- **A single-point reading cannot answer a question about change** - and the two axes fail the same way. *History:* to claim you introduced something, compute the property on the base commit too; a current-state grep answers "does this exist", never "is this new". Three of four duplicate top-level identifiers I called mine predated the branch, and the rename that justified would have left one of four inconsistent. *Time:* one post-event read cannot separate a fix that failed from a system that changed twice - sampling at +60ms and +660ms is what told a stale ARIA attribute from a listbox the library genuinely reopened.
- **A fixture field identical across every case it covers is dead, not passing.** Diff each field across a baseline's own cases before trusting it as a regression net: one constant everywhere is either constant by construction or reading a node that does not exist, and normalizing `null` to `""` is what disguises the second as the first. The sign narrows it for free: a constant `true`, non-empty string, or count of 1 or more cannot come from a probe that found nothing, so only a constant `0`/`false`/`null` needs an injection control - which is what cut eleven always-identical fields down to the three worth testing `[2026-08-23]`. Eighth shape in the `feedback-verify-my-own-verification` memory in the `EH-dataportal` project store.
- **A positive control rules out one explanation for a negative - count the explanations first.** Before reporting "it didn't load", "it didn't fire", "it isn't there", list every innocent reading that would look identical. Three explanations need three arms, not one control, and factorizing is the cheap way to get them: vary scope and the feature under test together, so each cell kills a different confound. "Does `~/.claude/rules/` honour `paths:`" looked like one probe and was a 2x2 - wrong frontmatter, an unread rules directory, and a dead hook all produce the same empty log. Incident: the `factorize-controls-for-a-negative-result` memory in the `claude-skills` project store.
- **A positive control proves the probe can fire; it does not establish recall** - and when the control instance is also the one whose vocabulary you wrote the probe from, it is circular, confirming only that the pattern matches the text it was derived from. A sweep for unsourced external claims validated itself on a dense cluster in `site-wide` §12 and reported zero across three other audit docs; a wider pattern found them in all three, and the sweep had also missed four files outright while reporting a word count that nearly matched. To assert a zero, derive the probe's terms from the definition of what you are looking for rather than from the hits you already have, or validate against a held-out instance. A cheap tell available at the time: count hits per file - if the file whose vocabulary you drew the pattern from holds an outsized share of them, the probe is circular.
- **In a two-arm comparison, perturb the variable under test - never an input both arms share.** Perturbing the shared input moves both arms together, so the test passes whichever way the mechanism works. This harness proves its probes by editing a committed baseline, and that injection cannot test the base-branch control job: the baseline is what *both* the head sweep and the base run compare against, so both go red and the verdict reads "the data moved" when the truth is that the baseline was edited. The discriminating arm needs the edit in the site source instead `[2026-08-24]`. **Then run the shared-input injection as the OTHER arm.** Until it does, the both-red branch and everything gated on it has never executed `[2026-08-25: the base control's RED verdict and its artifact upload]`.
- **One probe's positive control does not validate the others in the same harness.** A control that fires proves *that* probe can fire, not that the sweep beside it ran to completion. Any probe with a stop condition must emit why it stopped - input exhausted, or its own guard tripped - and its count checked against an expectation derived independently. Seventh shape in the `feedback-verify-my-own-verification` memory in the `EH-dataportal` project store: a keyboard sweep ended at 20 of 128 stops while an axe control beside it fired correctly.
- **A test run under conditions where the effect cannot occur is not evidence against it.** A positive control proves the *instrument* can fire; it does not prove the *conditions* could produce the thing being looked for. A measurement showing that an in-flight-request check "never binds" ran against a warm HTTP cache, where the fetch resolves instantly and the check has no window in which to bind - it established the check inert *when cached*, said nothing about the cold case the theory was about, and was written into the code as a disproof anyway `[2026-08-23]`. Before reporting a negative, state the conditions under which the effect would appear and confirm the test met them. **For an intermittent effect, agreement across N runs is weak evidence at any N** - the same session called a capture race absent three separate times on agreeing runs, which is what an intermittent failure looks like until it isn't. Reproduce it on demand or argue from mechanism, and say which you are doing.
- **An eval or test prompt must not hand over the facts the thing under test is supposed to go find.** A prompt that narrates the session back to the agent scores identically for a model that read the transcript and one that didn't - the grounding step it was meant to exercise becomes invisible. Put required prior state in the expected output as a precondition, not in the user's mouth.
- **Before deleting content as "already covered elsewhere", verify the *claim* survives, not the keyword.** A grep proving the term appears does not prove the surviving copy asserts the same thing - and the copy you are deleting may be the newer one. Applies to memory hooks, duplicate doc sections, and consolidating audit findings. **When moving or splitting a document, check claim by claim, not section by section** - dropping content because its *category* is covered elsewhere is what makes a move lossy, and the loss is invisible in the diff.
